# 创建子代理定义文件

本文档介绍如何编写子代理（sub-agent）定义文件，以及相关的背景知识和注意事项。

## 文件格式

子代理定义文件使用 **Markdown + YAML frontmatter** 格式（`.md` 文件）：

```markdown
---
name: agent_name
description: 该子代理的简要描述
tools: ["tool_a", "tool_b"]
---

系统提示词正文写在这里。
```

YAML frontmatter（`---` 之间的部分）存放元数据配置，Markdown 正文部分即为子代理的 **系统提示词**。

## 存放位置

| 类型 | 路径 | 说明 |
|------|------|------|
| 系统内置 | `api/agent/tools/sub_agent/default_agent_def/*.md` | 随代码一起部署，所有用户共享 |
| 用户自定义 | 用户 JuiceFS 文件系统的 `sys/agents/*.md` | 运行时从用户空间加载 |

加载优先级：**用户自定义定义会覆盖同名的系统内置定义**。

## Frontmatter 字段参考

### 必需字段

| 字段 | 类型 | 说明 |
|------|------|------|
| `name` | `str` | 子代理的唯一标识符，用于调用时指定 `agent_name` 参数 |
| `description` | `str` | 子代理功能的简要描述，会展示在工具描述列表中供主代理选择 |
| `tools` | `list[str]` | 子代理可使用的工具名称列表 |

### 可选字段

| 字段 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `skills` | `list[str]` | `[]` | 子代理应加载的技能名称列表 |
| `default_context_mode` | `str` | `"standalone"` | 默认上下文模式，可选值见下方说明 |
| `default_should_feedback` | `bool` | `true` | 默认是否要求子代理通过 `feed_message` 反馈结果 |
| `disable_completion_callback` | `bool` | `false` | 是否禁用子代理完成后的回调通知 |
| `service` | `str \| null` | `null` | 指定子代理使用的 LLM 服务名，为 null 时继承调用方的服务 |
| `mcp_server_config` | `dict \| null` | `null` | MCP 服务器配置，会完全替换（而非合并）基础会话配置中的 MCP 配置 |
| `before_agent_start_hook` | `str \| null` | `null` | POSIX 路径字符串，子代理启动前在用户容器中执行的脚本路径 |

### 字段详解

#### `tools`

列出子代理在执行过程中可使用的工具名称。子代理启动时，系统会根据此列表生成配置覆写（overlay），**未列出的工具将被禁用**。

`feed_message` 由 `default_should_feedback` 参数单独控制，不需要在此字段中列出。

可用的工具名称取决于系统中注册的工具，常见的包括：
- `read_file`、`edit_file`、`write_file`、`move_file`、`copy_file`、`delete_file`、`list_directory` — 文件操作
- `bash` — 执行命令
- `sub_agent` — 嵌套调用子代理
- `load_skill`、`skill_advisor` — 技能管理

#### `default_context_mode`

决定子代理运行时的上下文隔离程度：

- **`standalone`**（默认）：创建一个全新的独立分支，子代理从空白上下文开始运行。适用于完全独立的任务。
- **`fork`**：从当前任务 fork 出新分支，子代理继承调用方已有的对话上下文。适用于需要基于现有对话继续工作的场景。

调用时可通过 `context_mode` 参数覆盖此默认值。

#### `default_should_feedback`

- `true`（默认）：子代理将启用 `feed_message` 工具，可以向主代理反馈执行结果。
- `false`：子代理无法使用 `feed_message`，适合不需要与主代理通信的一次性任务。

调用时可通过 `should_feedback` 参数覆盖此默认值。

#### `disable_completion_callback`

- `false`（默认）：子代理执行完成后，系统会向调用方分支发送一条系统提醒消息，通知主代理子代理已完成。
- `true`：不发送完成通知。适用于"发射后不管"（fire-and-forget）的场景。

#### `service`

指定子代理使用的 LLM 服务名称（如 `"gpt-4o"`、`"claude-sonnet"` 等）。为 `null` 时继承调用方当前使用的服务。

可用于让不同子代理使用不同模型，例如简单任务使用轻量模型以节省成本。

#### `mcp_server_config`

MCP（Model Context Protocol）服务器配置。如果设置，将**完全替换**基础会话配置中的 MCP 配置（使用 `$replace` 语义）。为 `null` 时清除 MCP 配置。

#### `before_agent_start_hook`

指定一个 POSIX 路径（如 `/home/user/scripts/setup.sh`），子代理启动前会在用户的容器中执行该脚本：
- 执行命令：`bash {hook_path}`
- 超时时间：120 秒
- 脚本的 stdout/stderr 输出会作为消息注入到子代理的上下文中

适用于在子代理工作前准备环境（如拉取代码、安装依赖等）。

#### `skills`

列出子代理需要加载的技能名称。子代理启动时，系统会自动对比当前已加载的技能和此列表，生成加载/卸载指令。

## 系统提示词正文

Markdown 正文（frontmatter 之后的部分）就是子代理的系统提示词。这段文本会以 `<SUB_AGENT_DEF>` 标签包裹后注入到子代理的消息流中。

编写要点：
- 明确说明子代理的角色和能力边界
- 给出具体的工作流程和步骤指引
- 如果启用了 `should_feedback`，提示子代理使用 `feed_message` 工具向主代理反馈

## 完整示例

### 基础示例

```markdown
---
name: code_reviewer
description: 代码审查助手，检查代码质量并给出改进建议
tools: ["read_file", "bash"]
default_context_mode: standalone
default_should_feedback: true
---

你是一个专业的代码审查助手。

你的工作流程：
1. 读取需要审查的代码文件
2. 检查代码质量、潜在问题和改进空间
3. 通过 feed_message 工具将审查结果反馈给主分支

审查维度：
- 代码风格和可读性
- 潜在的 Bug 和边界情况
- 性能问题
- 安全隐患
```

### 高级示例（含 hook 和 MCP）

```markdown
---
name: project_builder
description: 项目构建助手，负责编译、测试和打包
tools: ["bash", "read_file", "write_file"]
skills: ["build_tools"]
default_context_mode: standalone
default_should_feedback: true
disable_completion_callback: false
service: gpt-4o
mcp_server_config:
  servers:
    build_server:
      command: "node"
      args: ["build-mcp-server.js"]
before_agent_start_hook: /home/user/scripts/prepare_build_env.sh
---

你是一个项目构建助手。

你的任务：
1. 检查项目结构和配置
2. 执行编译
3. 运行测试
4. 打包构建产物

完成后通过 feed_message 工具反馈构建结果。
```

## 运行时行为

### 消息注入顺序

子代理启动后，系统按以下顺序注入消息：

1. **系统提示词** — 定义文件中的 Markdown 正文，`<SUB_AGENT_DEF>` 标签包裹
2. **Hook 输出**（如有） — `before_agent_start_hook` 脚本的执行结果
3. **任务描述** — 调用者传入的 `task` 参数，`<EXTERNAL_MESSAGE>` 标签包裹
4. **技能管理指令**（如有） — 需要加载/卸载的技能列表
5. **反馈说明**（如启用） — 告知子代理使用 `feed_message` 工具

### 配置覆写机制

子代理启动时，系统会生成一个配置覆写（overlay），其行为：

- `tools` 中列出的工具 → 强制启用
- 未列出的工具 → 强制禁用
- `feed_message` → 由 `should_feedback` 单独控制
- `mcp_server_config` → 使用 `$replace` 语义完全替换（而非合并）

### 别名（Alias）机制

每个子代理分支会被分配一个 6 位随机字母数字别名（如 `a7x3`）。主代理可以通过别名引用子代理分支，用于发送后续指令。

### 完成回调

子代理执行完成后（除非 `disable_completion_callback: true`），系统会向调用方分支插入一条系统提醒，触发调用方重新处理消息，以便主代理检查子代理的工作结果。

## 注意事项

1. **name 唯一性**：`name` 在同类定义中必须唯一。用户自定义定义与系统内置定义同名时，用户定义覆盖系统定义。
2. **工具可用性**：`tools` 中列出的工具名称必须是系统中已注册的工具。如果列出了不存在的工具，不会报错但该工具不会生效。
3. **YAML 语法**：frontmatter 使用标准 YAML 语法。字符串列表推荐使用 `["a", "b"]` 行内写法以保持紧凑。
4. **编码**：定义文件必须使用 UTF-8 编码。
5. **frontmatter 不可省略**：即使只需要 `name` 和 `description`，也必须包含 `---` 分隔的 YAML frontmatter 块。
6. **hook 路径**：`before_agent_start_hook` 必须是有效的 POSIX 路径，指向用户容器中实际存在的脚本。
7. **system_prompt 可以为空**：如果 Markdown 正文为空，系统只会注入任务描述和其他辅助消息。但建议始终提供有意义的系统提示词。
